設計の前提

ここから他のすべてが導かれます。

同時に動くのは常に1つ。 だからサイドバーは「稼働中」と「プロジェクト」の2ブロックに割れ、 稼働中の1件だけがサービスを展開します。詳細を持てるのは動いている1つだけという構造が、 そのままツリーの形になります。

この一点で、よくある「プロセス管理ツール的な表」が消えます。ポート・PID・ステータス列が全プロジェクト分並ぶ画面は、 同時起動する世界のUIです。1つしか動かないなら、詳細は動いている1つにだけ必要で、残りは名前と行き先だけあればいい。

もうひとつの軸は安全性です。「ポート競合や終了失敗時は次を起動しない」は文言でなく画面構造で守ります。 切替と失敗はシート（モーダル）で出し、その間サイドバーに手が届きません。押せるボタンが無ければ、危険な同時操作は起こりません。

ウィンドウにした理由

最初はメニューバーのポップオーバーで設計しましたが、ウィザード・ログ・Expo QR と3つもポップオーバーの外に出すことになりました。 収まらないものが多すぎるというシグナルです。加えて頻度が非対称でした。

操作頻度所要向いている形
切り替える1日3〜5回2秒ポップオーバー
ログを見る1日数十回数分ウィンドウ
QRを出すExpo作業日は頻繁数分ウィンドウ
プロジェクト追加月に数回数分ウィンドウ

レアで速い操作にだけ最適化して、頻繁で遅い操作にコストを払わせていたのが前案でした。 ウィンドウを主、メニューバーを従にすると、この配分が逆転します。

形態を変えると、インタラクションの原則が1つ変わります。 ポップオーバーでは「行クリック＝実行」でしたが、ウィンドウでは「行クリック＝選択、実行は明示的なボタン」がmacOSの作法です。 これは安全側にも効いて、サイドバーの誤クリックで切替が始まることがなくなります。 速さはメニューバー（v2）が別途1クリックで担保します。

01

情報設計

3階層のツリーと、8つの状態。

ツリー構造がモデルそのもの

階層要素選ぶと右に出るもの
1稼働中（0〜1件）プロジェクト概要。展開してサービスを見る
2サービスそのサービスのログ。Expoならインスペクタも開ける
1プロジェクト（停止中）構成の要約と「切り替える」ボタン。前回のログも読める

停止中のプロジェクトも展開できます。前回落ちた理由を調べたいのは実際よくあるので、 止まっていてもログには到達できるべきです。ただし既定は折りたたみ、状態ドットは灰色。

必須／任意はサイドバーに出しません。行が窮屈になるうえ、日常的に見る情報ではないからです。 サービスを選んだときの見出し行（Web · :3000 · 必須）と、失敗時の文章で示します。

状態モデル

停止中 → 起動中 → 稼働中 → 一部停止

「起動中」は listen 開始とヘルスチェック通過の2段階を持ちます。listenしただけでは緑にしません。

稼働中 A → 終了中 A → ゲート：必須ポートの解放を検証 → 起動中 B

ゲートで不合格なら 切替失敗 へ。B は起動せず、A の残存状態を明示して停止します。

状態は8つ。

停止中 起動中 稼働中 一部停止 終了中 切替中 失敗 残存あり

うち一部停止と残存ありは、握りつぶしがちだが必ず可視化すべき状態です。 任意サービスが落ちても「稼働中」とだけ表示するのは silent fallback にあたります。

形の使い分け

丸 ●
状態。緑＝稼働、灰＝停止、橙＝注意、赤＝失敗、青（点滅）＝遷移中。
角丸四角 ▢
プロジェクトの識別。頭文字＋色。状態の色と絶対に混ざらないよう、形で分離する。
赤い数字バッジ
未読の stderr 行数。状態ではないのでドットの色は変えない。Next.jsのコンパイルエラーのようにプロセスが生きたままエラーを吐くケースを「失敗」にすると、状態が信用できなくなる。
色だけに頼らない
状態には必ずテキストラベルを併記（「稼働中 12分」）。色覚特性への配慮であり、スクリーンショット共有時にも効く。

クリック数

やりたいことウィンドウのみ（v1）メニューバー併用（v2）
いま何が動いてる？2（⌘Tab → 見る）0
別プロジェクトへ切替3（⌘Tab → 選択 → 実行）2
ログを見る2（⌘Tab → サービス選択）2

正直に言うと、切替は前案より1クリック増えます。それを買い戻すのがメニューバー（v2）です。 代わりにログとQRが速くなり、こちらは回数が桁違いに多い。トレードとしては勝ちだと考えています。

03

切替と失敗

安全性のロジックが、そのままシートの構造になっています。

切替は「Aを停止 → ゲート → Bを起動」の2フェーズです。フェーズの境目に破線のゲート行を置き、 ポート解放の検証がここで走ることを視覚化します。ゲートが通らなければ下半分は永遠に点灯しません。

ゲートが見るのは必須サービスのポートだけです。任意サービスのポートが埋まっていても切替は止めません （起動時に失敗すれば「一部停止」として現れ、原因はログに出る）。止める条件を絞ることで、 ゲートが「本当に危険なときだけ止まる」ものになります。

シートにしている理由は見た目ではありません。シートが出ている間はサイドバーに手が届かないのが目的です。 前案でポップオーバーからプロジェクト一覧を「描画しない」ことで守っていた性質を、ウィンドウではモーダルで守ります。

失敗の種類いつ既定ボタン破壊的な選択肢
ポート競合ゲート閉じる占有プロセスを終了して再試行
終了できない停止フェーズ切替を中止強制終了して続行（SIGKILL）
起動直後に落ちた起動フェーズログを開くなし（再試行は非破壊）
任意サービスの失敗起動フェーズシートを出さないなし

破壊的な操作を既定ボタンにしない。 「強制終了して続行」は赤文字の非塗りボタンで、⏎ が当たらない位置に置きます。 既定は常に安全側に倒れる方 — つまり切替を中止して、いまの状態のまま止まる方です。

失敗シートには必ず「現在の状態」を書く。 「Bell は停止しました。Penta は起動していません。」のように、 両方のプロジェクトが今どうなっているかを1行で断言します。 中途半端な状態を黙って放置しないための、この設計で最も重要な要素です。

失敗シートの「ログを開く」はシートを閉じて移動する。 落ちたサービスをサイドバーで選択した状態にしてからシートを閉じるので、 閉じた瞬間に原因のログが目の前にあります。ここもウィンドウにして初めて成立する導線です。

プロジェクト追加

独立ウィンドウをやめ、メインウィンドウのシートにしました。上の「プロジェクト追加」から開けます。

手入力を最小化
package.json / supabase/config.toml / docker-compose.yml / app.json を走査して候補を提示。ユーザーはチェックを外す作業だけをする。

最後にドライラン
実際には起動せず、ポート空き・コマンドの存在・ディレクトリの妥当性だけ検証する。初回の失敗を登録時点で潰す。

後から足す前提。ただし何を載せるかは今決めておきます。

色

アクセントカラーを自分で決めません。システムのアクセントカラー（ユーザーがシステム設定で選んだ色）をそのまま使います。 これがネイティブに馴染ませる最も効く一手で、同時に「アプリの色」と「状態の色」の衝突も避けられます。 彩度を持つのは下の5色だけで、それはすべてシステム定義色です。

ウィンドウ本体は不透明（windowBackgroundColor）、サイドバーだけ .sidebar マテリアルで わずかに透ける。ログ領域は textBackgroundColor（白／#1C1C1E）にして、読む面であることを地の色で示します。 メニューバーのポップオーバーだけは .popover マテリアル（vibrancy）。

SwiftUI 実装への対応

React参照実装の責務をSwiftUIへ対応付けます。プロダクションコードはSwiftで実装します。

コンポーネント責務
<MainWindow>ツールバー・サイドバー・詳細・インスペクタ・シートの配置
<Sidebar>稼働中／プロジェクトの2ブロック。選択のみを発火し、実行はしない
<ServiceRows>起動順（またはトグルで終了順）に並ぶ。未読エラーのバッジを持つ
<LogPane>選択中サービスのログ。検索・追従・消去
<ExpoInspector>QR・URL・接続モード・到達性の警告
<Sheet>phase を見て TransitionView / ErrorView / AdoptView / Wizard を出し分ける
<GateRow>停止側の実測ポート解放と、起動側の対象ポート確認を pending / passed / blocked で表示
<MenuBarPopover>v2。同じ state を読むが、行クリックで即実行する別の面

状態は { phase, activeId, selection, services, gate, error, logs } の単一オブジェクト。 phase が 'switching' | 'failed' | 'adopt' のときシートを出し、 その間サイドバーの onSelect を配線しないのではなく、シート自体がイベントを遮ります。 disabled 属性に頼らないのは、スタイルの都合で外れうるからです。モーダルは構造で遮ります。

08

決定事項

レビューで確定した6点。形態を変えても中身は変わりません。

a

「切替を中止」＝ A は止め切る、B は起動しない

確定。SIGTERM送出済みのプロセスへの取り消しは実装できないため、中止は「起動しない判断」だけを指します。 ボタン名は「切替を中止」のまま、下の補足文で「{A} の停止は最後まで実行し、{B} は起動しません」と毎回明示します。

画面: 切替シートの左下。起動フェーズに入ると自動で無効化され、理由が文章で出ます。

b

ゲートは必須サービスのポートだけ見る

確定。任意サービスのポートは検証しません。埋まっていれば起動時に失敗し「一部停止」として現れ、 原因はログに出ます。止める条件を必須だけに絞ることで、ゲートが「本当に危険なときだけ止まる」ものになります。

副次的な効果: 検証項目が減るのでゲートが速くなり、「検証中…」を独立ステップにする必要がなくなりました。

c

外部プロセスも終了してよい。ただし3つだけ例外を作る

殺してよい、で問題ありません。実務上ほとんどは自分が手で立てた npm run dev です。 ただし事故る経路が3つあるので、そこだけ塞ぎます。

①PIDの取り違え。lsof で調べてから kill するまでの間にプロセスが死ぬと、 OSが同じPIDを別プロセスに再利用します。kill 直前にもう一度「そのPIDがまだそのポートを持っているか」を確認してから送る。

②Docker管理下のプロセス。コンテナの中身をPIDで殺すとコンテナが中途半端に残ります。 親プロセスを辿ってDockerデーモン配下と判定できたら、kill ではなく docker stop を実行する。

③システムのDB。Postgres.app や Homebrew の postgres が 5432 を持っているケース。 オーナーが自分でない、または launchd 管理下と判定できたら終了ボタンを出さず、PIDのコピーだけにする。 これを殺すと他の作業まで壊れ、復旧が手作業になります。

画面: 失敗・ポート競合シート。SIGTERM → 猶予5秒 → 残っていればSIGKILLの再確認、という二段構えにします。

d

種別ごとの既定ヘルスチェック。設定は不要にする

MVPの線引き：TCP接続だけでは緑にしません。Next.jsは listen した直後は 200 を返さないので、 TCP到達＝緑にすると「緑なのに開けない」が起きます。かといって全サービスにURL設定を強いるとウィザードが重くなる。

そこでサービス種別ごとに既定のヘルスチェックを内蔵します。Webは GET / がタイムアウトと5xx以外を返すこと、 Supabaseは /rest/v1/、Expoは Metro の /status、Dockerは compose ps が healthy。 ユーザーは何も設定しません。上書きは詳細設定に隠します。

画面: 「応答待ち」シーン。ウィンドウ化したことで、警告バナーとログが同じ画面に並ぶようになりました。

e

プロセスは残す。次回起動時に実態から検証して引き継ぐ

「検証できたほうが良い」を、状態をディスクに保存せず、毎回実プロセスから再構築すると解釈しました。 保存した状態を信用すると、クラッシュや強制終了のあとに嘘の状態が残ります。

Dev Switcher を終了してもプロセスは残します。次回起動時は保存済みのPIDが生きているかと、 期待するポートを実際にlistenしているかを両方確認し、一致したものだけを引き継ぎます。

ログはサービスごとに分ける

確定。混ぜると読めません。サイドバーのサービスを選ぶ構成にしました。 分離の弱点である「他で何か起きても気づかない」は、サービス名の右に出る未読エラー数バッジで補います。

失敗シートに出す末尾6行は、落ちたサービスのstdout+stderrを時系列のまま出します。 stderrだけに絞ると「直前に何をしていたか」が消えるためです。
