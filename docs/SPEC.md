## 1. 目的

Dev Switcher は、ローカル開発環境を GUI から起動・停止・切り替える macOS アプリである。複数のプロジェクトを行き来する開発者が、切替のたびにターミナルを開き直し、各プロセスの起動・停止コマンドと使用ポートを確かめる負担をなくす。

単なるコマンドランチャーではない。次の開発環境を起動する前に、現在の開発環境が停止し、使っていたポートが解放されたことを実測で確認する。別の開発環境のプロセスやデータベースへ黙って接続する事故を防ぐことを最優先とする。

特定の技術スタック専用にはしない。通常の開発プロセス（`pnpm dev`、worker、watcher など）は種類を問わず登録でき、コンテナなどコマンド終了後も残る資源は「管理対象スタック」として、Dev Switcher が同梱する実装（Supabase、Docker Compose）だけを扱う。

## 2. 利用者とアプリの形態

利用者は macOS でローカルに複数の Web・モバイル・バックエンドプロジェクトを切り替える開発者で、対象のディレクトリを自分の Mac へ配置済みであることを前提とする。Windows と Linux は対象外とする。

アプリは通常の macOS アプリで、メインウィンドウ 1 枚で開発環境、プロセス、管理対象スタック、ポート、状態、ログを確認できる。Swift 6、SwiftUI、必要箇所のみ AppKit で実装し、外部パッケージはアプリ更新用の Sparkle だけを使う。App Sandbox は無効とする。利用者が選んだ複数のローカルディレクトリへ継続的にアクセスし、その配下で開発コマンドを起動し、外部プロセスとポートを検査する必要があるためである。選択先が Git リポジトリかどうかは判定しない。

## 3. 概念モデル

```text
開発環境 shop-web
├─ 作業ディレクトリ「Web」（/Users/example/GitHub/shop-web）
│  ├─ プロセス Web       pnpm dev
│  ├─ プロセス Worker    pnpm worker
│  └─ 管理対象スタック Supabase（type: supabase）
└─ 作業ディレクトリ「Native」（/Users/example/GitHub/shop-native）
   └─ プロセス Expo      pnpm start
```

### 3.1 開発環境

開発環境は、まとめて起動・停止する単位である。名前、識別色、作業ディレクトリの一覧、プロセスの起動順、管理対象スタックの一覧、今回の起動対象を持つ。コード上の型名は互換性のため `ProjectDefinition` のままだが、UI と文書では「開発環境」と呼ぶ。開発環境自体は代表ディレクトリを持たない。

### 3.2 作業ディレクトリ

作業ディレクトリは表示名（`Web`、`Native` など）と絶対パスを持ち、そこから起動するプロセスと管理対象スタックをまとめる。リポジトリという別概念は持たず、Git リポジトリ、モノレポ内のサブディレクトリ、通常のディレクトリを同じように登録できる。同じパスを 1 つの開発環境内に重複登録できない。パスは作業ディレクトリに 1 回だけ指定し、所属するプロセスとスタックへ共通に適用する。

### 3.3 プロセス

プロセス（コード上の `ServiceDefinition`）は、起動後もフォアグラウンドで動き続ける通常のコマンドである。名前、表示用タグ、起動コマンド、任意の停止コマンド、使用ポート、代表ポート、既定で起動対象にするか、起動失敗時に開発環境全体を止めるか、を持つ。

タグは `web`、`expo`、`worker` のような表示用の自由文字列で、起動・停止・判定の挙動を一切変えない。タグからポートやコマンドを推測しない。

1 つのプロセスが複数ポートを持てる。ポートを持たない worker や watcher も登録・停止できる。

Dev Switcher はプロセスを独立したプロセスグループとして起動し、子・孫プロセスを含めて管理する。コマンドの終了後もコンテナなどの資源が残るものは、プロセスとして管理しきれない。Docker 系のコマンド（実行ファイル名が `docker` または `docker-compose`）をプロセスとして登録することは拒否しないが、「停止はプロセスグループ単位であり、コンテナは残り得る」ことを検証時に警告する。警告は表示するだけで登録を妨げない。コンテナの起動・停止まで管理したい場合は、管理対象スタックとして登録する。

### 3.4 管理対象スタック

管理対象スタック（managed stack）は、起動コマンドが終了した後も Docker などの上に残る資源群を、Dev Switcher が同一性・状態・停止権限を持って管理する単位である。プロセスとは別のエンティティとして開発環境に属し、いずれか 1 つの作業ディレクトリに所属する。

管理対象スタックの種類（type）は Dev Switcher が同梱する実装に限る。現在は `supabase`（Supabase CLI のローカルスタック）と `dockerCompose`（Docker Compose プロジェクト）の 2 種類である。利用者が任意のコマンドを書いて停止方法や観測方法を宣言する仕組みは提供しない。観測できないときに停止中へ倒さないこと、外部の資源へ黙って停止操作をしないことを、利用者定義のコマンドに対して保証できないためである。

スタックは名前、種類、種類ごとの設定、使用ポート、代表ポート、既定で起動対象にするか、起動失敗時に開発環境全体を止めるか、を持つ。種類ごとの契約は 6 章で定める。

### 3.5 起動対象と失敗時の扱い

プロセスとスタックのそれぞれについて、次の 2 つを別の設定として扱う。

| 設定 | 値 | 意味 |
| --- | --- | --- |
| 起動対象（`enabledByDefault` と今回の上書き） | する／しない | 一括起動で起動するか。しないものは「対象外」 |
| 失敗時の扱い（`failurePolicy`） | `block` | 起動に失敗したら開発環境全体を失敗にし、今回起動したものを巻き戻す |
| | `continue` | 起動に失敗しても後続を起動し、開発環境を「一部停止」とする |

今回の起動対象は開発環境ごとに保存する（「今日は Expo も含める」を覚える）。保存するのは設定であって稼働状態ではない。対象外は失敗ではない。一括起動から外し、個別にも起動していないものは警告や「一部停止」に含めない。

### 3.6 起動順と停止順

一括起動では、管理対象スタックを開発環境内の登録順にすべて起動してから、プロセスを起動順に起動する。停止はその逆で、プロセスを停止順（既定は起動順の逆、明示指定も可）にすべて停止してから、スタックを登録順の逆に停止する。データベースなどのスタックに依存するプロセスが、スタックより先に起動・後に停止しないようにするためである。

### 3.7 用語

| 用語 | 意味 |
| --- | --- |
| 停止 | Dev Switcher（利用者の操作を含む）がプロセス・スタック・開発環境を止めること。signal、停止コマンド、強制停止のいずれも含む |
| 終了 | プロセスやコマンドが自ら終わること（exit）と、アプリ自体の終了（quit）に限って使う。Dev Switcher の停止操作には使わない |
| 実測 | 設定値ではなく、プロセス・ポート・コンテナを観測して得た事実 |
| 引き継ぎ | Dev Switcher が起動していない稼働中の対象を、利用者の承認または手掛かりの再検証により管理下へ入れること |
| 手掛かり | アプリ再起動後に再検証する対象を特定するための保存情報。稼働状態そのものではない |
| 残存 | 停止操作をしたのに停止を確認できず、資源が残っている状態 |
| 管理関係 | スタックを Dev Switcher が停止してよい根拠（`launched` / `adopted` / `restored`） |
| 外部 | Dev Switcher が起動も引き継ぎもしていないプロセス・スタック |

## 4. 排他切替の原則

同時に起動できる開発環境は最大 1 つとする。並行起動やポートの自動割当は行わない。開発環境 A から B への切替は、必ず次の順で行う。

1. A で実際に起動または引き継いでいた全プロセスを停止順に停止する
2. A で管理関係を持つ管理対象スタックを停止し、各スタックが `notRunning` になったことを実測する
3. A のプロセスが実際に使用していた全ポート（実測値）の解放を確認する（ゲート）
4. B の管理対象スタックについて、6 章の確認内容どおりに既存スタックの停止、起動、引き継ぎを行う
5. B のプロセスを起動順に起動する

手順 1〜3 のいずれかに失敗した場合、B を 1 件も起動しない。停止側の確認を先に行い、停止しきれなかったプロセス・スタックとポートを原因として提示する。

管理対象スタックの停止完了は、ポートではなく種類ごとの実測状態 `notRunning` で判定する。スタックのポートは Docker のプロキシが保持し、PID からスタックへ所有を辿れないためである。ゲートの対象は通常プロセスの実測ポートだけとする。6.3 の確認は手順 1 より前、何も変更しないうちに行い、手順 4 では承認内容を再観測で照合してから実行する。

起動前に B の設定ポートが空いているかは確認しない。空いていても起動時に取得できるとは限らず、埋まっていても起動できることがあり、確認は保証にならない。設定ポートは表示と「開く」URL のための補助情報であり、起動可否や起動成功の判定根拠にしない。同じ設定ポートを持つプロセスが複数あっても起動を拒否・スキップせず、OS が先に bind したものがポートを得る。取得できずに終了したものは通常の起動失敗として `failurePolicy` に従い、自分で別ポートを選んで生存したものは起動成功として実測ポートを表示する。

ゲート（手順 3）と既存スタックの扱いの確認（6.3）は、どちらも `failurePolicy` を使わない。落ちても続行するプロセスが握っていたポートも必ず確認する。

## 5. 日常操作

### 5.1 一括起動

停止中の開発環境を選び、今回の起動対象を確認して起動する。他の開発環境が起動済みなら、それは 4 章の切替になる。

起動対象に管理対象スタックが含まれる場合は、何も変更する前に 6.3 の確認フローを実行する。確認が必要なら利用者の承認を得るまで、切替元・切替先・既存スタックのいずれも変更しない。

プロセスの起動成功は、既定の初期観測期間（3 秒）中に終了せず、観測終了時点でも管理下にあることで判定する。判定に HTTP リクエストは使わない。設定ポートへ問い合わせると、同じポートを先に取った別プロセスの応答を自分の応答と誤認するためである。表示は「起動済み」とし、HTTP で応答することは保証しない。スタックの起動成功は 6 章の種類ごとの実測で判定する。

起動途中で `failurePolicy: block` のプロセスまたはスタックが失敗した場合は、今回 Dev Switcher が起動したものだけを逆順で停止し、後続を起動しない。引き継いだスタックは巻き戻し対象に含めない（6.4）。

### 5.2 停止

起動済みの開発環境を停止する。停止対象は設定ではなく、実際に起動または引き継いだプロセス・スタックから決める。ポートを持たないプロセスも停止する。プロセスの停止方法は 7 章、スタックの停止は 6 章に従う。停止しきれなかったものは「残存あり」として、対象とポート・PID・理由を表示する。

停止側は管理関係で判断する。管理関係を持つスタックは、実測状態が `unknown` でも対象限定の停止コマンドを実行し、その後に `notRunning` を確認できなければ残存として表示する。6 章の「`unknown` のとき何も変更しない」は、起動・引き継ぎ・既存スタックの停止確認（6.3）側の規則であり、自分が管理するスタックの停止には適用しない。停止できたかどうかは実測で決め、`unknown` を停止済みとは扱わない。

### 5.3 切替

4 章の手順で行う。切替中は他の開発環境の起動・停止操作を受け付けない。B の起動フェーズ（手順 4）に入る前までは「切替を中止」を受け付け、中止は「A の停止は最後まで行い、B を起動しない」ことを意味する。起動フェーズに入った後は中止を受け付けない。

### 5.4 起動済み環境への追加起動

起動済みの開発環境で、対象外または停止中の通常プロセスを 1 件ずつ追加起動できる。追加起動は今回だけで、一括起動の対象設定を変更しない。開発環境全体を停止した後の次の一括起動は、保存済みの対象設定に従う。

追加起動でも通常の初期観測を行い、ログと実測状態を表示する。失敗した場合は原因を表示し、操作前から動いていた他のプロセス・スタックを停止しない。失敗は失敗時の扱いに従って開発環境の「一部停止」または「失敗」へ反映する。追加起動したプロセスも個別に再起動でき、開発環境の停止・切替では停止対象に含める。

追加起動したプロセスもアプリ終了後に残す。起動前に手掛かりを保存できなければ追加起動せず、起動後に保存できなければ追加した 1 件だけを停止する。その停止に失敗した場合は残存と復旧手段を表示する。

管理対象スタックの追加起動は提供しない。スタックの起動は一括起動に限る。

### 5.5 再起動

起動済みの開発環境で、稼働中の通常プロセス 1 件を再起動できる。対象だけを停止し、停止前に実測した対象のポートの解放を確認してから起動する。再起動中と再起動失敗時に、他のプロセスとスタックは停止しない。

作業ディレクトリ単位の操作、プロセスの個別停止、管理対象スタックの個別起動・個別再起動・個別停止は提供しない。

### 5.6 開く

起動中の開発環境について、`openUrl` を持つポートをブラウザで開ける。作業ディレクトリを Finder で表示できる。

## 6. 管理対象スタック

### 6.1 契約

管理対象スタックの各種類は、次の項目をすべて定義する。定義できない項目がある種類は同梱しない。

| 契約項目 | 意味 | Supabase | Docker Compose |
| --- | --- | --- | --- |
| 同一性（ID） | 同じスタックかどうかを決める値 | `supabase/config.toml` の `project_id` | Compose のプロジェクト名（6.7 の規則で決定） |
| ID の一意性 | 同じ種類のスタックの中で、登録済みの全開発環境にわたって一意 | 同左 | 同左 |
| 1 開発環境あたりの上限 | `enabled` にかかわらず数える | 1 件 | 制限なし |
| 排他範囲 | 起動時に停止を確認する既存スタックの範囲 | マシン上の全ローカル Supabase スタック | なし（対象と同じ ID だけを見る） |
| 状態の観測 | `running` / `degraded` / `notRunning` / `unknown` の判定方法 | 6.6 | 6.7 |
| 起動 | 起動コマンドと、起動成功の判定 | `supabase start` ＋ `running` の実測 | `docker compose up -d` ＋ `running` の実測 |
| 対象限定の停止 | 1 つの ID だけを止めるコマンドと、停止完了の判定 | `supabase stop --project-id <id>` ＋ `notRunning` の実測 | `docker compose -p <name> -f <file>... --profile '*' stop` ＋ `notRunning` の実測 |
| 引き継ぎ可否 | 同じ ID の稼働中スタックを、起動せずに管理下へ入れられるか | 可 | 可 |
| 禁止オプション | どの経路でも生成・実行しない操作 | `--all`、`--no-backup` | `down`、`rm`、`kill`、`-v` / `--volumes`、`--rmi`、`--remove-orphans`、`-V` / `--renew-anon-volumes` |

排他範囲が「マシン全体」の種類は、対象と別の ID が稼働していれば停止を確認する。「なし」の種類は、対象と別の ID のスタックを観測も停止もしない。別の Compose プロジェクトがポートを握っていれば、`up` の失敗として通常の起動失敗になる。

### 6.2 実測状態と管理関係

スタックの状態と、Dev Switcher が停止してよいかどうかは別に管理する。

| 実測状態 | 共通の意味 |
| --- | --- |
| `notRunning` | 対象 ID の資源が稼働していないことを確認できた |
| `running` | 対象 ID の資源が種類ごとの基準で正常に稼働していることを確認できた |
| `degraded` | 対象 ID の資源が一部だけ稼働している、または異常であることを確認できた |
| `unknown` | 観測コマンドの失敗、未対応の応答などにより、上の 3 つを確定できない |

`unknown` を `notRunning` へ倒すことはどの経路でも行わない。`unknown` のとき何も変更しないのは、起動・引き継ぎ・既存スタックの停止確認（6.3）の側である。管理関係を持つスタックを停止する側は、`unknown` でも対象限定の停止を試み、`notRunning` を確認できなければ残存として表示する（5.2）。

| 管理関係 | 意味 |
| --- | --- |
| `launched` | 今回 Dev Switcher の起動コマンドが成功し、直後の実測で `running` を確認できた |
| `adopted` | 外部で起動された同じ ID のスタックを、利用者の承認後に引き継いだ |
| `restored` | 管理関係（`launched` / `adopted` / `restored` のいずれか）を持つ手掛かりの ID と fingerprint が現在の設定と一致し、実測が `running` または `degraded` だった（11 章） |

通常の停止・切替で Dev Switcher が停止してよいのは、この 3 つの管理関係を持つスタックだけである。状態が `running` または `degraded` であることだけを理由に、外部スタックを停止してはならない。

管理関係を持つスタックが `notRunning` と観測された時点で、その管理関係を解除し、対応する手掛かりを破棄する。外部で停止された後に同じ ID のスタックが外部から起動されることがあり、古い `launched` / `adopted` / `restored` のまま停止対象にしないためである。解除後に同じ ID が稼働していれば、手掛かりの無い外部スタックとして扱う。

### 6.3 起動時の確認フロー

今回の起動対象に管理対象スタックが含まれる場合、切替元・切替先のどちらも変更する前に、起動対象の各スタックについて次を実測し、処理内容を決める。

| 実測結果 | 動作 |
| --- | --- |
| 対象が `notRunning` で、排他範囲内に別スタックもない | 確認なしで対象を起動し、`running` を確認する |
| 対象と同じ ID が `running` | 引き継ぎ確認を出す。承認後は `adopted` として登録し、起動コマンドを実行しない |
| 対象と同じ ID が `degraded` | 停止して起動し直す確認を出す。承認後に対象限定の停止、`notRunning` の確認、起動、`running` の確認の順で復旧する |
| 排他範囲内に別 ID が `running` または `degraded` | 既存スタックを停止して切り替える確認を出す。承認後に既存スタックを停止し、`notRunning` を確認してから対象を起動する |
| いずれかの判定が `unknown` | 確認を出さず、既存スタックも切替元・切替先も変更せず、観測できなかった理由を表示する |

切替元の開発環境に属し、すでに管理関係を持つスタックは、通常の切替確認で停止が承認済みである。スタック固有の停止確認を重ねて出さない。

対象と同じ ID の `running` と、排他範囲内の別スタックが同時に存在する場合は、別スタックを停止し、対象が引き続き `running` であることを再確認してから引き継ぐ。対象が `degraded` なら対象を含む全停止対象を停止してから対象だけを起動し、対象が `notRunning` なら別スタックを停止してから対象を起動する。いずれの場合も、対象がすでに `running` なら起動コマンドを重ねて実行しない。

### 6.4 確認・実行・失敗の規則

確認は、起動対象の全スタックについて、引き継ぐ対象・復旧する対象・停止する全対象を 1 つのシートにまとめて表示する。各行に種類と ID を必ず表示し、登録済みの定義と一致する場合は開発環境名、スタック名、作業ディレクトリを、一致しない場合は「未登録」と表示する。停止後に対象の起動が失敗しても、停止した既存スタックを自動で再起動しないことも表示する。引き継ぎでは、引き継いだ後は Dev Switcher から停止・切替できること、現在のスタックへ起動時の引数（Supabase の `--exclude`、Compose の追加引数など）を再適用しないことを明示する。キャンセルを既定選択とし、キャンセル時は既存スタック、切替元、切替先のいずれも変更しない。

承認後、最初の変更操作の直前に、確認時の対象集合と各状態、対象設定の構成同一性（fingerprint）を再観測する。確認時と一致しなければ何も停止・起動せず、最新の内容で確認を出し直す。停止は ID ごとに対象を限定したコマンドで 1 件ずつ実行し、各対象が `notRunning` になったことを確認する。途中で失敗した場合は後続の停止と起動を中断し、すでに停止したスタックは再起動しない。失敗した ID、停止済みの ID、未処理の ID を結果に残す。全件の停止後にも、排他範囲内に予期しないスタックが現れていないか再観測してから、対象を起動または引き継ぐ。

確認のキャンセル、`unknown`、再観測の不一致、既存スタックの停止失敗は、スタックの起動失敗ではない。スタックの `failurePolicy` にかかわらず操作全体を中断する。

対象の起動コマンドは、実行直前に `notRunning` を再観測してから実行し、コマンドの成功と起動後の `running` の実測が揃った後だけ `launched` とする。起動処理が失敗した後の実測が `notRunning` なら `failurePolicy` を適用する。`running` / `degraded` / `unknown` なら、別のターミナルから起動された可能性を否定できないため停止権限を取得せず、自動停止もしない。この場合は `failurePolicy` にかかわらず中断し、利用者が再度起動したときの実測から、引き継ぎまたは停止の確認へ進む。

【PM 判断待ち: 論点 1】

`adopted` のスタックは、今回 Dev Switcher が起動したものの巻き戻し対象に含めない。引き継ぎ後に別のプロセスまたはスタックが `failurePolicy: block` で失敗した場合は、今回起動したものだけを停止し、引き継いだスタックは `adopted` のまま残す。開発環境を「残存あり」と表示し、利用者が明示的に停止できる導線を維持する。

### 6.5 観測のタイミング

スタックは、アプリ起動時、アプリのフォアグラウンド復帰時、起動・停止・切替の各操作の直前に再観測する。定期ポーリングは行わないため、バックグラウンド中に外部で操作された状態は、次の復帰または操作まで表示へ反映されない場合がある。

どのタイミングの観測でも、管理関係を持つスタックが `notRunning` なら 6.2 のとおり管理関係を解除して手掛かりを破棄する。

アプリ起動時とフォアグラウンド復帰時の観測は、保存済み手掛かりの自動再検証と表示更新だけを行う。確認の表示、管理関係の取得、停止は行わない。手掛かりなしで `running` の同じ ID のスタックは外部スタックとして表示し、利用者がそのスタックを含む開発環境の起動または切替を実行したときだけ 6.3 の確認を出す。

### 6.6 Supabase

管理する対象は、`supabase start` を実行する CLI プロセスではなく、その終了後も Docker 上に残るローカル Supabase スタックである。

**同一性**: Supabase CLI が同一マシン上のローカルプロジェクトを区別する値である `supabase/config.toml` の `project_id` で判定する。起動コマンドに `--workdir` があればそのディレクトリ、なければ所属する作業ディレクトリを基準に設定ファイルを読む。環境変数による暗黙の workdir 変更は許可せず、CLI を実行するときは `SUPABASE_WORKDIR` を環境から除く。`project_id` を取得できない（ファイルが無い、読めない、トップレベルの `project_id` が無い・空・重複・解釈不能）場合は、ディレクトリ名・コンテナ名・ポートで補わず、保存と起動を失敗させる。専用の読み取り処理が未対応の TOML エスケープも、バックスラッシュを削除するなどの部分変換をせず、解釈不能として失敗させる。

**起動コマンドの形式**: `supabase start`、`pnpm exec supabase start`、`npx supabase start`、`pnpx supabase start` の形式に限る（`supabase@<version>` の指定と、Supabase CLI のグローバルオプションは可）。`pnpm supabase start`、`yarn supabase start`、`bunx supabase start` などそれ以外の呼び出しは、スタックとしては受け付けない。プロセスとしての登録可否は `docs/SCHEMA.md` 5 章の判定に従う（該当すれば検証エラー、`supabase` の直前がオプションの形は警告。15.2）。この場合は上の 4 形式のいずれか（パッケージの CLI を使うなら `pnpm exec supabase start`）へ書き換えてスタックとして登録する。停止コマンドは利用者が指定できず、起動コマンドと同じ CLI 呼び出し形式・設定ディレクトリから `status` と対象限定の `stop` を導出する。起動コマンドに `--all` または `--no-backup` を含めることはできない。

**状態の観測**: Supabase CLI がコンテナへ付ける `com.supabase.cli.project` ラベルを使い、`docker ps -a` と `docker inspect` 相当の読み取り専用コマンドで全ローカルスタックを列挙する。ID はコンテナ名から切り出さずラベル値を使う。

| 状態 | 判定 |
| --- | --- |
| `notRunning` | 対象 `project_id` のコンテナが存在しない。`supabase stop` が保持するバックアップ用 volume は数えない |
| `running` | DB コンテナが running かつ healthy。設定ディレクトリが既知なら、対象の `supabase status` の成功も確認する。設定ディレクトリが不明な外部スタックは DB コンテナの実測だけで判定する |
| `degraded` | コンテナが 1 件以上あり、DB コンテナの欠損・停止・unhealthy のいずれかを確認できた |
| `unknown` | Docker の実行失敗、出力の解析失敗、ラベル欠落、DB コンテナ候補の重複、health が starting、未対応の状態、DB は healthy だが `supabase status` が失敗 |

`running` は DB と状態確認コマンドの成功までを意味する。起動時の設定（`--exclude` など）が現在のスタックに適用されていることや、全 HTTP エンドポイントの応答までは保証しない。

この観測は読み取り専用である。Docker のコンテナ・volume を直接起動・停止・削除しない。

**上限時間**: Supabase CLI の各コマンド（`start`、`status`、`stop`）の実行上限は 300 秒とする。`start` の成功後に `running` を、`stop` の成功後に `notRunning` を、それぞれ最大 60 秒まで再観測して待ち、期限の時点の状態で判定する。

**上限と排他範囲**: 1 つの開発環境に登録できる Supabase スタックは 1 件まで、`project_id` は登録済みの全開発環境で一意とする。同じ Supabase を使う Web と Native は 1 つの開発環境にまとめる。Dev Switcher はマシン上で複数のローカル Supabase スタックを同時に稼働させないため、起動時は管理外を含む全ローカルスタックを排他範囲として扱う。複数スタックの同時利用と、同じスタックを複数の開発環境から共有する構成は対象外とする。

**禁止**: `supabase stop --all` と `--no-backup` は、コマンドの構築時と実行の直前の両方で拒否する。

### 6.7 Docker Compose

管理する対象は、Docker Compose（`docker compose` サブコマンド）のプロジェクトとして作られたコンテナ群である。スタンドアロンの `docker-compose` は対象外とする。

**Compose ファイル**: Dev Switcher は、起動・観測・停止のすべてのコマンドに、同じ Compose ファイルを `-f` で明示して渡す。`files` を指定した場合はその全ファイルを指定順に渡す。省略した場合は、作業ディレクトリ直下の `compose.yaml`、`compose.yml`、`docker-compose.yaml`、`docker-compose.yml` からこの優先順で最初に見つかった 1 つを基本ファイルとし、同じディレクトリに対応する override ファイル（`compose.override.yaml`、`compose.override.yml`、`docker-compose.override.yaml`、`docker-compose.override.yml` のうち基本ファイルと同じ系統で最初に見つかったもの）があれば、その後ろに続けて渡す。作業ディレクトリ直下に基本ファイルが無ければ、親ディレクトリを探さず検証エラーにする。解決したファイルの一覧は構成同一性（fingerprint）に含める。

**プロファイル**: 起動・観測には、設定した `profiles` を同じ `--profile` として付ける。停止だけは常に `--profile '*'` を指定し、同じプロジェクト名の全 profile を対象にする。設定外の profile で外部起動されたコンテナも停止対象となるため、編集・詳細画面と引き継ぎ・復旧・既存スタック停止の確認に、この停止範囲を表示する。

**環境変数**: Compose の対象を暗黙に変える `COMPOSE_PROJECT_NAME`、`COMPOSE_FILE`、`COMPOSE_PROFILES` を、Dev Switcher が実行する Compose コマンドの環境から除く。プロジェクト名とファイルは `-p` と `-f` の明示指定で固定する。Compose ではコマンドラインの指定が環境変数より優先されるため、Compose が `.env` を読んでも操作対象のプロジェクトは変わらない。起動・観測で `profiles` を省略した場合に `.env` の `COMPOSE_PROFILES` が効くかどうかは Compose の挙動に任せる。停止は明示した `--profile '*'` を使う。

**同一性**: Compose のプロジェクト名で判定する。名前は次の Dev Switcher 独自の規則で決め、決めた名前を起動・観測・停止のすべてのコマンドへ `-p <name>` として必ず明示する。

1. スタック定義の `projectName`
2. 上で解決した Compose ファイルのトップレベル `name:`
3. プロジェクトディレクトリ名。プロジェクトディレクトリは、Dev Switcher が渡す最初の `-f` ファイルを含むディレクトリとする（`files` を省略した場合は作業ディレクトリ）

この規則は Docker の名前決定と似ているが同じではない。Docker は環境変数や `.env` の `COMPOSE_PROJECT_NAME` も参照するが、Dev Switcher は `.env` を読まないため参照しない。ターミナルから `docker compose up` で起動したスタックを同じスタックとして引き継ぎたい場合は、ターミナル側で使われているプロジェクト名（`docker compose ls` で確認できる）を `projectName` に明示する。特に `.env` で `COMPOSE_PROJECT_NAME` を設定しているプロジェクトや、`-f` で別ディレクトリのファイルを指定しているプロジェクトでは、明示しないと別の名前になり得る。

`name:` は、解決した Compose ファイルのトップレベルの `name:` の値だけを読む。引用符なしの値、または引用符で囲んだエスケープなしの値に限る。変数展開（`${...}`）を含む、複数のファイルで値が異なる、その他解釈できない場合は推測せず検証エラーにし、`projectName` の明示を求める。

`projectName` と `name:` の値は、英小文字・数字・`-`・`_` のみで先頭が英小文字か数字、という規則を満たさなければ検証エラーとし、変換しない。プロジェクトディレクトリ名から決める場合だけ、英小文字化と規則外の文字の除去を行い、結果が空または規則外なら `projectName` の明示を求める。

同じ種類の中での一意性により、別々の作業ディレクトリでもディレクトリ名が同じ（例: 2 つの `web`）なら保存時に重複エラーになる。その場合は `projectName` で区別する。

**起動**: 作業ディレクトリで `docker compose -p <name> -f <file>... [--profile <profile>...] up -d [追加引数...]` を実行する。追加引数（`upArguments`）は `docs/SCHEMA.md` 7.2 の許可リストに載っている形式だけを受け付ける（サービス名、`--build`、`--wait` など）。コマンドの実行上限は 300 秒とする（イメージの取得やビルドを伴うため Supabase と同じ値を仮置きしている）。コマンドが成功した後、`running` になるまで最大 60 秒再観測し、期限の時点の状態で判定する。`running` なら起動成功、それ以外は 6.4 の「起動処理が失敗した後」の規則に従う。

**状態の観測**: `docker compose -p <name> -f <file>... [--profile <profile>...] ps --all --format json` 相当の読み取り専用コマンドで、対象プロジェクトのコンテナを列挙する。実行上限は 60 秒とする。出力は 1 行 1 オブジェクトの JSON と JSON 配列の両方を受け付ける。2026-11-12 に Docker Compose v5.5.0 で、設定外の profile で外部起動されたコンテナもこの出力に含まれることを確認した。他の実行環境でも Phase B の受け入れ条件に従い実機確認する（18 章 Docker Compose）。

コンテナの状態を次のように分類する。

| 分類 | コンテナの状態 |
| --- | --- |
| 正常稼働 | `running` で、healthcheck が無いか `healthy` |
| 異常稼働 | `running` で `unhealthy`、または `restarting`、`paused` |
| 停止済み | `exited`、`created`、`dead` |
| 判定不能 | `running` で health が `starting`、`removing`、その他の未対応の値 |

プロジェクトの状態は、次の表を上から順に評価し、最初に当てはまった行で決める。

| 優先 | 条件 | 状態 |
| --- | --- | --- |
| 1 | `docker` を実行できない、Docker が応答しない、出力を解析できない、判定不能のコンテナが 1 件以上ある | `unknown` |
| 2 | 正常稼働と異常稼働のコンテナが合わせて 0 件（停止済みだけが残る、またはコンテナが無い） | `notRunning` |
| 3 | 異常稼働のコンテナが 1 件以上ある、または停止済みのコンテナが 1 件以上ある | `degraded` |
| 4 | すべてのコンテナが正常稼働 | `running` |

判定はコンテナが存在するサービスだけを対象とし、Compose ファイルの全サービス定義とは突き合わせない。Compose ファイルを Dev Switcher が完全には解析しないためである。このため、正常に完了して終了する one-shot のサービス（初期化用コンテナなど）を含むプロジェクトは、起動後も `degraded` と判定される。これは現在の既知の制約とする。

【PM 判断待ち: 論点 2】

**対象限定の停止**: `docker compose -p <name> -f <file>... --profile '*' stop` を実行する。同じプロジェクト名の全 profile を対象にし、起動・観測に設定した profile には限定しない。実行上限は 300 秒とする。成功後、`notRunning` になるまで最大 60 秒再観測し、期限の時点で `notRunning` でなければ停止失敗として残存を表示する。`down` は使わない。コンテナとボリュームを削除する操作は、Supabase の `--no-backup` と同じ扱いで禁止する。停止後もコンテナは exited として残り、次の起動で再利用される。

**上限と排他範囲**: 1 つの開発環境に複数の Compose スタックを登録できる。プロジェクト名は登録済みの全開発環境の Compose スタックの中で一意とする。排他範囲は持たず、対象と別の名前の Compose プロジェクトを観測も停止もしない。

**`.env` との関係**: Compose 自身がプロジェクトディレクトリの `.env` を読むのは Compose の挙動であり、Dev Switcher は `.env` を読まない。Compose の起動時に行われるイメージの取得やビルドも Compose の挙動として扱い、Dev Switcher が別途インストール・更新操作をすることはない。

## 7. 通常プロセスの停止

プロセスの停止方法は、停止コマンド（`stop`）の有無で決まる。

`stop` を設定していないプロセスは、プロセスグループへ SIGTERM を送り、既定の猶予（10 秒）の間に全メンバーの終了を待つ。猶予後も残る場合は停止失敗として残存を表示し、自動で SIGKILL を送らない。

`stop` を設定したプロセスは、停止時に SIGTERM を送らず、その停止コマンドを実行する。停止コマンドは起動コマンドと同じく実行ファイルと引数を分けた構造化データで、指定した作業ディレクトリで実行し、出力は対象プロセスのログへ流す。停止コマンドの完了（上限 30 秒）を待った後、対象のプロセスグループの終了を既定の猶予（10 秒）まで待つ。プロセスグループが終了すれば停止成功とする。停止コマンドが失敗または 30 秒で完了しなかった場合はその旨をログと結果に残し、そのうえでプロセスグループが残っていれば停止失敗として残存を表示する。この場合も自動で SIGKILL を送らない。

停止コマンドを実行する前に対象のプロセスグループを実測し、すでに存在しなければ停止コマンドを実行せず停止済みとする。停止コマンドは独立したプロセスグループで起動する。30 秒で完了しなかった停止コマンドは Dev Switcher が起動したプロセスなので、そのプロセスグループへ SIGTERM を送り、10 秒の猶予後も残っていれば、停止コマンドのプロセスグループも残存として表示する（自動で SIGKILL は送らない）。

どちらの場合も、停止状態はプロセスグループの実測で決め、停止コマンドの終了コードだけで決めない。

**強制停止**: 残存したプロセスについて、利用者が明示的に「強制停止」を選んだ場合だけ、送信直前にプロセスの同一性を再検証してから SIGKILL を送る。強制停止は既定ボタンにせず、送信前に再確認する。強制停止できるのは、Dev Switcher が起動したか、手掛かりから安全に引き継いだプロセスグループだけである。管理対象スタックには強制停止を提供しない。

**同一性の再検証**: ポート確認から signal 送信までの間に PID が再利用される可能性があるため、送信直前に開始時刻、実行ファイル、作業ディレクトリ、プロセスグループから同一性を再検証する。一致しなければ送信しない。

## 8. 状態表示

開発環境、プロセス、スタックについて、少なくとも次の状態を区別する。色だけで状態を伝えず、必ずテキストラベルを併記する。

| 状態 | 意味 |
| --- | --- |
| 対象外 | 今回の起動対象から外したもの。警告や一部停止に含めない |
| 停止中 | 動いていない |
| 起動中 | 起動処理中。プロセスは初期観測が終わっていない、スタックは `running` を確認していない |
| 起動済み | 初期観測を通過した、またはスタックの `running` を実測した。HTTP 応答は保証しない |
| 一部停止 | `failurePolicy: continue` のものだけが停止・失敗している開発環境。起動済みの一種 |
| 停止処理中 | 停止処理中 |
| 切替中 | 切替の停止・ゲート・起動のいずれか |
| 失敗 | 停止できない、ポートが解放されない、起動直後に終了した、のいずれか |
| 残存あり | 停止しきれなかったプロセス・スタック、または巻き戻さなかった引き継ぎ済みスタックがある |

一度も起動していない対象外は一部停止に含めない。今回追加起動したプロセスの失敗は含める。スタックには実測状態（`running` など）と管理関係（今回起動・引き継ぎ・再検証済み・外部）も表示する。

プロセスの状態は実測から判定し、ログの内容や出力先では変更しない。通知は、起動・停止・切替の失敗と、正常起動後に停止操作なしで通常プロセスが終了した場合に限る。

## 9. ポート表示

ポートの入力はプロセスとスタックのどちらでも任意とし、タグや種類から既定ポートを自動入力しない。ポートを 1 つ以上入力した場合は代表ポートをちょうど 1 つ指定する。同じ対象の中でポート番号を重複させない。異なる対象の間の同じ番号は拒否しない。

一覧では代表ポートと残りのポート数（`:54321 +2`）、詳細では全ポートをラベル付きで表示する。停止中の開発環境でも起動予定のポートを確認できる。停止元のポートが解放されないときは、そのポート番号、PID、コマンド、所有区分（Dev Switcher、外部プロセス、システムまたは別ユーザー）を表示する。プロセス名だけでなく、解放されていないポートを名指しする。

## 10. ログ

プロセスごとに stdout と stderr を時系列で 1 つのログとして表示する。stdout と stderr の本文は同じ通常色で表示し、ログの内容や出力先からエラーを判定・通知しない。stderr の行数はログ欄の補助情報として通常色で表示し、一覧に未読バッジは出さない。

既定では最新ログへ追従し、利用者が過去ログを読んでいる間は追従を止める。起動失敗時は原因の末尾ログ（stdout と stderr を時系列のまま）を失敗画面に表示し、そこから原因のログへ移動できる。正常起動後に停止操作なしで通常プロセスが終了した場合は、そのログへ移動できる通知を表示する。

停止後もログを保持し、同じ対象の次の起動試行を始める時点で表示行と行数をリセットする。管理対象スタックのログには、Dev Switcher が実行した起動・停止・状態確認コマンドの出力を表示する。全プロセスを混ぜたログ表示は提供しない。

## 11. アプリの終了・再起動と引き継ぎ

アプリを終了しても、起動中の開発プロセスと管理対象スタックは停止しない。アプリの終了をサーバー停止の意思表示として扱わない。

ディスクに保存した「動いている」という状態をそのまま信用しない。保存してよいのは開発環境の定義などの設定と、次回の実測対象を特定する手掛かりだけで、手掛かり自体を稼働状態として復元しない。

**プロセス**: 手掛かりとして PID、プロセスグループ、開始時刻、実行ファイル、作業ディレクトリ、記録時の実測ポートを保存する。次回起動時に、PID だけを信用せず開始時刻・実行ファイル・作業ディレクトリ・実測ポートを確認し、一致したものだけを候補にする。候補は「そのまま使う」（引き継ぐ）か「停止する」を選べ、安全に再利用できない残存では「そのまま使う」の代わりに「停止しない」を出す。「停止しない」対象がポートを占有していれば、次の切替をゲートが止める。プロセスが存在しないなど確実に古い手掛かりは自動で整理し、観測不能や定義の欠落など結論の出ない手掛かりは保持して理由を表示する。

**管理対象スタック**: 手掛かりとして種類、ID、構成同一性（fingerprint）、管理関係を保存する。アプリ起動時とフォアグラウンド復帰時に、次の順で再検証する。

1. 手掛かりが管理関係（`launched` / `adopted` / `restored` のいずれか）を持っている。前回すでに `restored` だった手掛かりも同じく再検証する（旧形式で管理関係を持たない手掛かりは、ここで止めて保持する）
2. 手掛かりの ID が、現在の設定から解決した ID と一致する
3. 手掛かりの fingerprint（設定ディレクトリ・起動コマンドなどの構成）が、現在の設定から作った fingerprint と一致する
4. その ID を実測する

1〜3 のどれかが成り立たない場合は、状態確認や停止のコマンドを実行せず、理由を表示して手掛かりを保持する。4 の実測が `running` なら `restored` として起動済みにし、手掛かりも `restored` として保存し直す。`degraded` でも `restored` として管理下に戻すが、起動済みにはせず「残存あり」として停止導線を出す。`notRunning` なら手掛かりを破棄する。`unknown` なら何も変えず、理由を表示して手掛かりを保持する。保存後に ID または設定が変わって再検証できない手掛かりは、状態確認や停止のコマンドを実行せず、理由を表示して保持する。現在の設定と不一致であることを確認できる手掛かりは、利用者が明示的に破棄できる。

## 12. 外部の資源と停止の権限

- 通常プロセスで停止対象にできるのは、Dev Switcher が起動したか、手掛かりから安全に引き継いだものだけとする
- それ以外の外部プロセスは自動停止せず、Dev Switcher から signal も送らない。識別情報を表示し、利用者が起動元のターミナルや管理ツールで停止する
- システムまたは別ユーザーが管理するプロセスには、停止操作を提供せず識別情報のコピーだけを提供する
- 管理対象スタックは、6.3 の確認を利用者が承認した場合に限り、表示した ID へ対象限定の停止コマンドを実行できる。この承認を他のスタックや通常の外部プロセスを停止する権限へ拡張しない
- Docker のコンテナを直接 `docker stop` / `docker kill` / `docker rm` しない。スタックの操作は 6 章の種類ごとのコマンドだけで行う

## 13. 実行上の禁止事項

Dev Switcher は、開発環境の起動・停止に必要な操作以外を自動実行しない。特に次を禁止する。

【PM 判断待ち: 論点 3】

- DB の reset、migration、seed
- 依存パッケージのインストール・更新
- `supabase stop --all`、`supabase stop --no-backup`
- `docker compose down`、`rm`、`kill`、ボリューム・イメージ・孤立コンテナの削除
- リポジトリやローカルファイルの削除・移動
- プロジェクト配下の `.env`、`.env.*`、`.envrc` の読み取り
- 未確認の自動検出コマンドの実行
- 必須値の欠落を既定値で補う silent fallback

コマンドは実行ファイルと引数を分けて保持し、利用者の入力をシェル文字列へ連結しない。GUI 起動時の `PATH` などの環境変数は、環境変数 `SHELL` が示す利用者のログインシェルで固定コマンド（`-lic '/usr/bin/env -0'`）を実行して取得する。`SHELL` が未設定・空・絶対パスでない・存在しない・実行できない・csh 系（`csh` / `tcsh`）である場合は、既定のシェルへ倒さず原因を表示して起動を止める。csh 系はログインシェル（`-l`）と `-c` を同時に指定できず、この方法で環境を取得できないためである。取得コマンドが失敗した場合も、最小の `PATH` へ黙ってフォールバックせず、原因を表示して起動を止める。利用者のコマンドの実行にログインシェルを使わない。

## 14. エラー時の原則

- 必須情報が欠けている、または不正な設定は、起動前・保存前に具体的なエラーにする
- 実行中の操作がある間は、他の起動・停止・切替・設定変更・引き継ぎを受け付けない
- 失敗画面には、切替元と切替先の現在状態を必ず 1 行ずつ断言する（例:「shop-web は停止しました。admin-console は起動していません。」）
- 起動途中で失敗した場合、今回起動したものだけを安全に停止する
- 以前の開発環境や停止した既存スタックを自動で再起動しない
- 破壊的な操作を既定ボタンにしない
- 観測できないことを「停止中」「空いている」と解釈しない

## 15. 開発環境の管理

### 15.1 追加と編集

「開発環境を追加」から、開発環境、作業ディレクトリ、プロセス、管理対象スタックを手動で登録できる。追加と編集は同じ 1 枚の画面で行う。作業ディレクトリを選んだとき、表示名が空ならパス末尾を入力補助として入れる。

編集できるのは、開発環境名と識別色、作業ディレクトリの追加・削除・並べ替え・表示名・パス、プロセスの追加・削除・並べ替え（起動順）・名前・タグ・起動コマンド・停止コマンド・ポート・起動対象・失敗時の扱い、管理対象スタックの追加・削除・並べ替え・名前・種類ごとの設定・ポート・起動対象・失敗時の扱いである。編集画面で扱わない既存値（明示した停止順、今回の起動対象など）は、保存時に保持して欠落させない。

起動済みの開発環境は編集できない。停止してから編集する。項目ごとに安全性を判定する例外は設けない。設定値と実状態のずれを避けるためである。この拒否は UI の無効化だけでなく、状態を変更する API の境界でも行う。

### 15.2 検証

保存前に次を検証し、問題があれば対象を特定できる具体的なエラーを表示する。一覧は `docs/SCHEMA.md` の検証規則を正とする。

- 必須値の欠落、空文字、重複 ID、名前の重複
- 作業ディレクトリの実在、絶対パス、所属関係の過不足
- 範囲外ポート、同じ対象内の重複ポート、代表ポートの欠落・複数
- スタックの種類ごとの設定、ID の解決、1 開発環境あたりの上限、同じ種類の中での ID の一意性（登録済みの全開発環境を対象とし、解決できない環境が 1 つでもあれば一意性を確認できたことにせず失敗させる）
- Supabase を起動するコマンドをプロセスとして登録すること（判定と例外は `docs/SCHEMA.md` 5 章。該当すれば検証エラーとして管理対象スタックでの登録を求め、`supabase` の直前がオプションの形は警告にとどめる）

検証は設定ファイル（`supabase/config.toml`、Compose ファイル）とディレクトリの読み取りだけで行い、Docker や各 CLI のコマンドを実行しない。件数超過や ID の重複も、コマンドを実行せずに検証エラーにする。Compose のプロジェクト名の解決もファイルの読み取りで完結させ、検証中に `docker`（`docker compose config` などを含む）を呼ばない。起動直前の ID の再解決も同じ方法で行う。

次は警告として表示し、保存を妨げない。

- Docker 系のコマンド（実行ファイル名が `docker` または `docker-compose`）をプロセスとして登録した場合: 停止はプロセスグループ単位であり、コンテナは残り得る
- Supabase の起動であり得るコマンドをプロセスとして登録した場合（`supabase` の直前がオプションの形。判定は `docs/SCHEMA.md` 5 章）: Supabase の起動なら管理対象スタックとして登録するよう案内する

起動直前にも、登録済みの全開発環境のスタック ID を解決し直す。解決不能または重複なら新しい起動・切替を止めるが、すでに管理下にあるものの停止導線は残す。

【PM 判断待ち: 論点 4】

### 15.3 登録解除

開発環境を Dev Switcher から登録解除できる。登録解除はローカルのリポジトリやファイルを削除しない。確認画面に、削除されない対象パスを明記する。起動済みの開発環境は、先に停止を求める。

### 15.4 設定の保存

開発環境の設定は、利用者の Mac の Application Support 配下へ、一時ファイルへ書いてから atomic に置き換えて保存する。形式は `docs/SCHEMA.md` の schemaVersion 4 とし、それより古い形式は読み込み時に変換する。変換の前後で、プロセス・スタックの ID、プロセス同士の相対的な起動順と停止順、今回の起動対象を維持する。3.6 の規則によりスタックがプロセスより前に起動し後に停止するため、変換で開発環境全体の起動順または停止順が変わる場合は、変換結果を保存するまで、読み込みのたびに対象の開発環境名と変わった内容を通知する。

【PM 判断待ち: 論点 5】

保存済み設定を読み込めない状態では、古いメモリ内容による追加・更新・起動を拒否する。停止は復旧手段として維持する。

各利用者のリポジトリ配置場所が異なることを前提とし、設定の Export、共通カタログ、クラウド同期は提供しない。

### 15.5 JSON からの一括追加

手動入力を繰り返さずに登録できるよう、AI などが作成した JSON から複数の開発環境を一括追加できる。保存形式と同じ形式（`docs/SCHEMA.md`）を使い、画面から形式説明とサンプルをコピーして AI へ渡せる。

ファイルを選ぶと、開発環境ごとに作業パス、起動順、コマンド、管理対象スタック、起動対象を表示し、設定の全項目も展開して確認できる。検証の警告もここで表示する。利用者が追加を実行するまで保存せず、取り込みによってプロセスやスタックを起動しない。

取り込みは新規追加に限る。登録済み設定とファイル内の重複、不正な値、存在しない作業ディレクトリは、手動登録と同じ検証で拒否する。確認後も保存直前に再検証し、失敗時は 1 件も追加しない。既存設定を読み込めない状態と、起動・停止・切替などの操作中は取り込みを受け付けない。CSV 取り込みと既存設定の一括更新は提供しない。

### 15.6 既存定義からの候補追加

追加・編集画面の作業ディレクトリごとに、直下の `package.json` と Compose ファイルから候補を読み込める。親・子ディレクトリ、workspace 内のパッケージ、Procfile は探索しない。読み込み・フォームへの反映ではコマンドを実行せず、設定も保存しない。

`package.json` の `scripts` を名前順に表示し、名前・本文・登録するコマンドを確認して選択する。名前から開発用途を推定して絞り込まず、初期選択は0件とする。登録コマンドは選んだ package manager の `run <script名>` とし、本文をシェル文字列として組み立て直さない。関連する pre/post script の実行と、コンテナ用 script の登録先については、出典横の詳細ボタンから確認できる。script の中身の安全性や、長時間動作することを保証する機能ではない。

package manager は直下の lockfile の存在で候補を決める。`pnpm-lock.yaml` は pnpm、`package-lock.json` / `npm-shrinkwrap.json` は npm、`yarn.lock` は yarn、`bun.lock` / `bun.lockb` は bun とする。同じ manager の複数ファイルは1種類と数える。1種類だけなら選択欄へ入れ、未検出・複数種類・ファイルの確認失敗では利用者の選択を求める。選択は変更できる。検出した lockfile と `packageManager` の宣言は詳細ボタンから確認できるが、自動インストールやバージョン切替は行わない。lockfile の内容は読まない。

Compose は 6.7 の規則で基本ファイルと override を解決し、1スタックの候補としてプロジェクト名と対象ファイルを表示する。確認した名前・ファイルを明示した設定として追加する。サービス・profile・ポートは推定せず、必要ならフォームで設定する。名前を解決できない場合は理由と手動登録の案内を表示する。停止範囲（同じプロジェクト名の全 profile）は出典横の詳細ボタンから確認できる。

読み取り対象は通常ファイルに限り、内容を読むファイルは各1 MiB以下とする。`.env`、`.env.*`、`.envrc` とそれらへの symlink は読まない。不正な JSON、空の script、解釈不能な Compose などは出典ごとにエラーを表示し、別の出典の候補と区別する。存在する不正な値を空の候補へ黙って置き換えない。

件数付きの追加ボタンで選択した候補だけをフォームへ反映する。反映直前に出典を再読し、確認時からの変更があれば反映せず読み直しを求める。既存の入力と既存対象同士の順序を保持し、新規フォームが用意した未入力1行だけを取り除く。名前が重複する場合は全候補の反映を止める。追加した候補は手動追加と同じく起動対象・失敗時 `block` とし、反映後のフォームで変更できる。通常プロセスの停止コマンド・タグ・ポートは補完しない。保存は既存のフォーム操作で行い、15.2 の検証を通す。

## 16. UI の原則

### 16.1 形態と構成

取り込み候補は出典ごとにまとめ、チェック・名前・コマンドを列で揃える。候補数に応じて高さを変え、フォーム全体のスクロールを使う。操作手順・保存前確認・追加完了の定型説明は常設しない。補足は詳細ボタン、判断に必要なエラーはその場に表示する。フォームでは各見出しの直下に対応する入力行を置く。

メインウィンドウ 1 枚を主とする（既定 880 × 544 pt、最小 720 × 460 pt）。ログを読む、設定を編集するといった頻繁で時間のかかる操作に合わせるためで、メニューバーは提供しない。ウィンドウでは「行クリックは選択、実行は明示的なボタン」とする。

サイドバーは「稼働中」（0〜1 件）と「開発環境」の 2 ブロックに分ける。稼働中の 1 件だけがプロセスとスタックを展開する。全開発環境のポート・PID・状態を並べる表は作らない。停止中の開発環境も展開でき、前回の失敗理由をログで確認できる。

| 選択 | 右側に出るもの |
| --- | --- |
| 稼働中の開発環境 | 概要と ⋯ メニュー（編集、Finder で表示、登録を解除） |
| プロセス | そのプロセスのログ |
| 管理対象スタック | 種類、ID、実測状態、管理関係、ポート、Dev Switcher が実行したコマンドのログ |
| 停止中の開発環境 | 起動対象のチェックリスト、「既定に戻す」、起動または切替のボタン |

シート（モーダル）は、進捗と判断が必要な場面に限る。停止を伴う別の開発環境への切替、失敗、アプリ起動時の引き継ぎ、管理対象スタックの確認、登録解除の確認、追加・編集、JSON 取り込みである。単純な起動・停止はシートを出さず、対象のボタン内にスピナーと「起動中」「停止処理中」、直下に現在の段階（`Web を起動（2/4）` など）を出す。高速に終わっても人工的な待ち時間は入れない。

失敗シートの「ログを開く」は、シートを閉じてから原因のプロセスを選択した状態にする。

| 失敗の種類 | いつ | 既定ボタン | 破壊的な選択肢 |
| --- | --- | --- | --- |
| 停止できない | 停止フェーズ | 切替を中止 | 強制停止して続行（SIGKILL、再確認つき） |
| ポートが解放されない | ゲート | 閉じる | なし（占有プロセスを名指しするが自動停止しない） |
| スタックの状態を確認できない | 確認前 | 閉じる | なし |
| 既存スタックを停止できない | 起動フェーズの前段 | 閉じる | なし |
| 起動直後に終了した | 起動フェーズ | ログを開く | なし（再試行は非破壊） |
| `continue` のものの失敗 | 起動フェーズ | シートを出さない | なし |

### 16.2 安全性の不変条件

実装が守るべき規則であり、ここを崩すと設計の意味が消える。番号はコード中の参照に使う。

- **I-1** 多重操作は状態を持つ層の API 境界で拒否し、UI の無効化に依存しない。起動・停止・切替・設定変更・引き継ぎの決着・再検証は、同時に 1 件しか取得できない排他トークンを通す
- **I-2** サイドバーは選択しか発火しない。切替・起動・停止は明示的なボタンだけで行う
- **I-3** ゲートを通らなければ起動フェーズに入らない。ゲートは停止元の通常プロセスの実測ポートの解放だけを見て、起動先の設定ポートは調べない。設定値と実測値を同じ経路へ流さない
- **I-4** 起動フェーズに入ったら中止を受け付けない
- **I-5** 失敗画面には必ず切替元と切替先の現在状態を書く。型で必須にする
- **I-6** 破壊的な操作を既定ボタンにしない。既定は常に「いまの状態のまま止まる」側に倒す
- **I-7** ログの内容を状態に昇格させない
- **I-8** 稼働状態をディスクに保存して信用しない。起動時は実測から再構築する
- **I-9** 起動済みの開発環境は編集させない

### 16.3 見た目

アクセントカラーを独自に決めず、システムのアクセントカラーを使う。彩度を持つ色はシステム定義色の 5 つに限る。

| 用途 | 色 |
| --- | --- |
| 起動済み | systemGreen |
| 注意・一部停止 | systemOrange |
| 失敗 | systemRed |
| 停止中 | systemGray |
| 選択・遷移中 | accentColor |

状態は塗った丸、対象外は色を持たない中空の丸、開発環境の識別は頭文字と利用者が選ぶ 8 色の角丸四角で描き、状態色と形で分離する。文字色は `labelColor` / `secondaryLabelColor` / `tertiaryLabelColor` の 3 段階とする。数字が並ぶ箇所は等幅数字にし、ポート・PID・ログ本文は SF Mono を使う。余白は 4pt グリッド、角丸は 10 / 7 / 6（ウィンドウ / カード / 行・ボタン）とする。アニメーションは遷移中を示す用途に限り（150〜200ms の ease-out）、視差効果を減らす設定ではスピナーだけを低速で残す。詳細な数値は `Sources/DevSwitcher/Features/DesignSystem/DesignTokens.swift` を正とする。

### 16.4 日本語・英語

日本語を維持し、Mac の言語設定（アプリ個別の優先言語を含む）で日本語・英語を選ぶ。優先言語の順に対応言語を探し、どちらも無い場合は英語を使う。選択はアプリ起動時に固定し、設定変更の反映には再起動が必要である。アプリ内の言語切替設定は設けない。

ボタン、状態、確認、エラー、補足、アクセシビリティの文言とコピー用の取り込みガイドを選択言語で表示する。利用者が付けた名前、パス、コマンド、外部コマンドの出力・ログは翻訳しない。設定 JSON のキー・値・ID、起動・停止・確認の判定を言語で変えない。翻訳リソースやキー、埋め込み引数の欠落は、別言語や空文字で補わずエラーとして検知する。

英語文書は `docs/en/` に置き、日本語文書を仕様の正として維持する。英語で説明が長くなる画面も既定・最小ウィンドウ内で折り返しやスクロールによって読めるようにする。

### 16.5 アプリの更新

配布版は Sparkle で新版を自動確認し、見つかったら通知する。ダウンロード・インストールは利用者の操作で始め、無断で自動インストールしない。アプリメニューに「アップデートを確認…」と「アップデートを自動確認」を置く。自動確認は初期値オンで、利用者がオフにした設定を次回起動時も保持する。システム情報の統計送信は無効とする。

更新に伴うアプリ終了でも、11 章の手掛かりの保存と操作完了待ちを通す。保存失敗・待機タイムアウトでは終了を取り消し、開発プロセスやスタックは停止しない。更新後は通常のアプリ起動と同じ再検証を行う。

更新情報と配布物は公開 GitHub Releases から HTTPS で取得し、EdDSA 署名で配布物を検証する。Release 下書きは通知対象にしない。Sparkle 未搭載の旧版からは、最初の一度だけ DMG で入れ替える。開発用の直接起動とローカル確認用アプリは更新確認を行わず、手動確認時に配布版を使う案内を出す。配布版の更新設定の欠落・不正はエラーとして表示する。

- HTTP readiness とカスタムヘルスチェック
- Procfile、workspace・子ディレクトリの自動探索と追加ウィザード（直下の package.json・Compose の候補追加は 15.6）
- 開発環境の複製、設定の Export、CSV 取り込み、既存設定の一括更新、共通カタログ、クラウド同期

- Windows／Linux 対応、利用者の操作なしでの更新インストール、UI の自動テスト

## 18. 受け入れ条件

### 開発環境の管理

- GUI から新規開発環境を登録でき、別リポジトリでも通常ディレクトリでも複数の名前付き作業ディレクトリとして登録できる
- 同じ作業ディレクトリに属する複数のプロセスとスタックに、パスを 1 回だけ指定できる
- 複数のプロセス、複数のポート、ポートを持たないプロセスを登録できる
- タグを自由な文字列で登録でき、タグの値で起動・停止の挙動が変わらない
- 管理対象スタックを Supabase と Docker Compose の両方で登録できる
- `docker` を実行ファイルとするプロセスを、警告を表示したうえで保存できる
- `docs/SCHEMA.md` 5 章の判定に該当する Supabase 起動コマンドをプロセスとして保存できない
- `supabase` の直前がオプションの形（SCHEMA 5 章の警告対象）は、警告つきでプロセスとして保存できる
- 停止中の開発環境を編集・登録解除でき、起動済みの開発環境は UI と API 境界の両方で拒否する
- 登録解除してもローカルファイルが削除されない
- schemaVersion 3 以前の設定を読み込んでも、プロセス・スタックの ID、プロセス同士の相対的な起動順と停止順、今回の起動対象が変わらず、`kind: "supabase"` のサービスが同じ ID の Supabase スタックになる
- 変換で起動順または停止順が変わる開発環境があれば、変換結果を保存するまで、読み込みのたびにその名前と変わった内容が通知される
- JSON で複数の開発環境を確認後に一括追加でき、取り込みによってコマンドを実行しない
- 重複・不正値・保存失敗では 1 件も追加せず、既存設定を保持する

### 既存定義からの候補追加

- scripts の本文と登録コマンド、lockfile の根拠、Compose の名前とファイルを確認して選択でき、初期選択は0件である
- manager の未検出・競合時に既定値で補完せず、利用者が選択できる
- 読み込み・反映・保存のいずれでも、検出したコマンドを実行しない
- 不正なファイルと候補0件を区別し、`.env` 等への symlink を読み取り前に拒否する
- 取り込み元の変更・候補名の重複ではフォームを部分更新せず、既存入力を保持する
- 選択した候補だけを既存フォームへ追加し、通常の保存前検証を通す

### 起動・停止

- スタックを登録順に起動した後、プロセスを設定順に起動する
- プロセスを停止順に停止した後、スタックを登録順の逆に停止する
- ポートを持たない起動済みプロセスも停止する
- 対象外のプロセス・スタックが警告や一部停止として扱われない
- 起動済み環境の対象外プロセスを今回だけ追加起動でき、一括起動の設定が変わらない
- 追加起動したプロセスも全体停止・切替で停止し、次の一括起動では対象外に戻る
- 追加起動の失敗、手掛かりの保存失敗で、操作前から動いていた他のプロセス・スタックを停止しない
- 失敗を許容するものだけが落ちた場合、一部停止と表示される
- 起動判定で HTTP リクエストを送らない

### 通常プロセスの停止

- `stop` のないプロセスはプロセスグループへの SIGTERM で停止し、猶予後も残れば残存として表示し、SIGKILL を自動送信しない
- `stop` のあるプロセスは停止コマンドを実行し、SIGTERM を送らない
- 対象のプロセスグループがすでに存在しなければ、停止コマンドを実行しない
- 30 秒で完了しない停止コマンドには、そのプロセスグループへ SIGTERM を送り、猶予後も残れば残存として表示する
- 停止コマンドの後にプロセスグループが猶予内に終了すれば停止成功、残れば残存として表示し、SIGKILL を自動送信しない
- 停止コマンドの失敗・タイムアウトがログと結果に表示される
- 強制停止は利用者の明示操作と再確認の後だけ、同一性を再検証してから行う

### 管理対象スタック（種類共通）

- 1 開発環境あたりの上限を超えるスタックを登録できない（Supabase は `enabled` にかかわらず 2 件目を拒否する）
- 保存・取り込みの検証中に、Docker・Supabase CLI・Docker Compose のコマンドを 1 件も実行しない
- 同じ種類の中で、登録済みの開発環境間に同じ ID を登録できない。異なる種類なら同じ文字列の ID でも登録できる
- ID を解決できないスタックを保存・起動しない
- 対象と同じ ID が `running` の場合、承認後に引き継ぎ、起動コマンドを実行しない
- 引き継いだスタックを開発環境の停止・切替で停止できる
- 引き継ぎ後に別のものが `failurePolicy: block` で失敗しても、引き継いだスタックを巻き戻さず、残存ありと停止導線を表示する
- 対象が `degraded` の場合、承認後だけ対象限定の停止、停止確認、起動を順に実行する
- 排他範囲内に別 ID が `running` または `degraded` の場合、承認と停止確認が完了するまで対象を起動しない
- 確認が必要な対象が複数ある場合は 1 つの確認に全件を表示し、承認後も各 ID を個別に停止する
- 確認後の再観測で対象・状態・設定が変わっていた場合、変更せず最新内容で確認を出し直す
- 確認をキャンセルした場合、既存スタック、切替元、切替先を変更しない
- 6.3 の確認フローで状態が `unknown` の場合、既存スタックの停止、対象の起動・引き継ぎへ進まない（管理関係を持つスタックの停止は次の項目に従う）
- 確認のキャンセル、`unknown`、停止失敗に `failurePolicy: continue` を適用しない
- 起動処理の失敗後に `notRunning` 以外が観測された場合、自動停止せず中断する
- アプリ起動・フォアグラウンド復帰・起動／停止／切替の直前に再観測し、アプリ起動と復帰だけでは確認を出さない
- `launched`、`adopted`、`restored` のいずれかの管理関係を持つ手掛かりから、アプリ再起動後に実測して `restored` にできる。`running` なら起動済み、`degraded` なら残存ありと停止導線を表示する。設定や ID が一致しない手掛かりでは状態確認・停止のコマンドを実行しない
- 管理関係を持つスタックが `notRunning` と観測されたら、管理関係と手掛かりを破棄する
- 管理関係を持つスタックが `unknown` でも、利用者の停止・切替では対象限定の停止を試み、`notRunning` を確認できなければ残存として表示する
- 通常の切替で、管理下のスタックの停止確認を二重に出さない

### Supabase

- `project_id` を取得できない設定、未対応の起動コマンド形式、`--all` / `--no-backup` を含む起動コマンドを保存できない
- 全ローカルスタックを排他範囲とし、別 `project_id` の稼働を確認なしに放置して対象を起動しない
- `supabase stop --all` と `--no-backup` をどの経路でも実行しない
- `SUPABASE_WORKDIR` を CLI へ渡さない

### Docker Compose

- プロジェクト名を `projectName`、`name:`、プロジェクトディレクトリ名の順で決め、規則外の値や変数展開を含む `name:` は保存できない
- 起動・観測・停止の全コマンドに同じ `-p <name>`、`-f <file>...` を付ける。起動・観測は設定した `profiles` を使い、停止だけは常に `--profile '*'` とする。`COMPOSE_PROJECT_NAME`、`COMPOSE_FILE`、`COMPOSE_PROFILES` を環境から除く
- 起動は `up -d` で行い、許可リストに無い追加引数（短いオプションの結合を含む）を保存できない
- 観測結果を 6.7 の優先順位の表どおり 4 状態へ分類し、停止済みコンテナだけが残る状態を `notRunning` とする
- 起動・停止の待機は期限まで再観測し、期限の時点の状態で判定する
- 停止は `stop` で行い、`down`、`rm`、`kill`、`-v`、`--rmi`、`--remove-orphans` をどの経路でも実行しない
- 対象と別の名前の Compose プロジェクトを観測・停止しない
- 実機確認: 同じプロジェクト名で、Dev Switcher の `profiles` と別の profile のサービスを外部から起動して稼働させた状態で、`-p` と `--profile` を付けた `ps --all --format json` がそのコンテナを出力するかを確認する。引き継ぎ確認で全 profile が停止対象と分かり、承認後に `--profile '*' stop` でそのコンテナも止まり、`notRunning` を確認できることも確かめる。出力しない場合は、観測が稼働中のコンテナを見落として `notRunning` と誤判定し得るため、観測コマンドの組み立て（`--profile` を付けない、または全 profile を対象にする）を見直してから Phase B を完了とする

### 切替

- 切替元の通常プロセスの実測ポートがすべて解放され、切替元のスタックが `notRunning` になるまで、切替先を 1 件も起動しない
- 切替先の設定ポートは起動前に検証せず、設定順に全プロセスの起動を試行する
- 停止しきれなかったプロセス・スタックとポートを特定できる
- 切替失敗時に、両方の開発環境の現在状態が表示される
- 起動フェーズ前の中止では切替元の停止を完了し、切替先を起動しない

### 再起動・引き継ぎ

- 稼働中の通常プロセス 1 件を再起動しても、同じ開発環境の他のプロセスとスタックを停止しない
- 再起動対象が使用していた実測ポートの解放前に、同じプロセスを起動しない
- アプリを終了しても開発プロセスとスタックが残る
- アプリ再起動時に既存プロセスを再検証でき、追加起動したプロセスも引き継ぎ・再起動・停止できる
- 保存済み PID と異なるプロセスを誤って引き継がない
- 外部プロセスを利用者の確認なしに停止しない

### 検証の方法
