# Dev Switcher — ロードマップ

- 作成日: 2026-10-16
- 関連文書: `docs/SPEC.md`、`docs/ARCHITECTURE.md`、`docs/SCHEMA.md`
- English: [Roadmap](en/ROADMAP.md)

社内 MVP（Supabase 専用の管理と通常プロセスの管理）を基準線とし、汎用ツールへ発展させる。最初の 3 段階（Phase A / B / C）で `docs/SPEC.md` の現行仕様を実装し、その後の項目は優先度順に検討する。各段階は既存の安全性（排他切替、停止側のゲート、観測不能を停止中へ倒さないこと、外部の資源へ黙って停止操作をしないこと）を維持し、`swift build` と `swift test` の成功を完了条件に含める。

## 現在の実装状況（2026-11-12）

- Phase A: 2026-10-19 に実装済み。
- Phase C: 設定 v4、旧形式からの移行と順序変更通知、タグ、通常プロセスの停止コマンド、編集・取り込み画面を実装済み。
- Phase B: 完了。Compose の設定解析、driver、登録・確認・詳細表示を実装済み。停止は `--profile '*'` で同じプロジェクト名の全 profile を対象にし、画面でも範囲を明示する。2026-11-12 に Docker Compose v5.5.0 で、設定外の profile の観測・確認後の引き継ぎ・停止と、通常の起動・停止・再起動を確認した。同日、利用者から検証完了の確認を得た。

## 1. 実装段階

### 推奨順: A → C → B

Phase A を最初に行うのは、挙動を変えないリファクタであり、既存の Supabase のテストで正しさを確かめられるためである。抽象を先に入れておけば、後続の段階は切替のトランザクションに触れずに済む。

C を B より先に行うのは、Docker Compose のスタックを定義する場所がデータモデルに必要なためである。B を先にすると、v3 の `kind` enum へ一時的に Compose を足し、C でもう一度変換することになる。これは `kind` を表示用タグにする方針とも矛盾する。C の後なら、B は種類を 1 つ追加する作業に閉じる。

C に含む「通常プロセスの停止コマンドの有効化」は、管理対象スタックの抽象に依存しない。必要なら A と並行して進めてよいが、`SwitchCoordinator` の preflight と停止処理に触れるため、同時に実装するときは worktree を分けるか触るファイルを分ける。

### Phase A: 管理対象スタックの抽象と Supabase の移し替え

目的は、Supabase 専用の型と分岐を種類共通の抽象（`docs/ARCHITECTURE.md` 4 章）へ移し、Supabase をその 1 実装にすることである。データモデルと保存形式（schemaVersion 3）は変えず、`kind: "supabase"` のサービスをアダプタでスタックとして扱う。

| 内容 | 完了条件 |
| --- | --- |
| `ManagedStackType` / `ManagedStackIdentity` / 状態・管理関係・観測・snapshot・確認 plan・承認の種類共通の型 | Supabase 専用の同名の型が Domain に残っていない |
| `ManagedStackDriver` と `SupabaseStackDriver`、`ManagedStackSupervisor`、`RuntimeRegistry` の `knownStacks` | Supabase の知識（ラベル名、CLI 形式、禁止オプション）が Supabase 実装の中に閉じている |
| `SwitchCoordinator` の確認フローを起動単位と種類共通の plan に置き換え | `kind == .supabase` の分岐が `SwitchCoordinator` から無くなる |
| エラー型と手掛かりの汎用化（手掛かりファイル v7） | v6 の手掛かりを読み込み、再起動後に `restored` にできる |
| `AppState` と確認シートの汎用化 | 画面の表示内容が現行と変わらない |

既存のテストの検証内容を変えずにすべて成功させる。型名の変更に伴う機械的な書き換えだけを許す。

### Phase C: タグ化、schemaVersion 4、通常プロセスの停止コマンド

目的は、データモデルを `docs/SCHEMA.md` の v4 にし、プロセスとスタックを別のエンティティにすることである。

| 内容 | 完了条件 |
| --- | --- |
| `ServiceKind` を自由文字列の `tag` に替え、`managedStacks` と `stackIDs` を追加 | v4 の往復保存、未知キーの拒否 |
| v3 → v4 の変換 | Supabase のスタック化、ID・起動順・停止順・起動対象の保持、順序が変わる場合の通知 |
| 起動順・停止順をスタック先行・後行に変更 | `docs/SPEC.md` 3.6 の順序をテストで確認 |
| Docker 系コマンドの警告、`supabase start` のプロセス登録の拒否、`kind == .docker` の起動拒否の撤去 | 警告では保存を妨げない |
| 通常プロセスの停止コマンド | `docs/SPEC.md` 7 章の受け入れ条件 |
| 編集画面・JSON 取り込み・`ProjectImportGuide.md` と `ProjectImportExample.json` を v4 に更新 | AI 向けガイドから v4 の JSON を作成・取り込みできる |
| 画面ラベルを `docs/SPEC.md` の「停止」「終了」の用語に合わせる（「終了中」→「停止処理中」など） | `docs/ARCHITECTURE.md` 8 章の 3 ラベルが変わっている |
| `type: "dockerCompose"` は Phase B まで未対応として扱う | 保存・取り込みで `dockerCompose` のスタックを「未対応の種類」として検証エラーにし、編集画面でも選べない |

### Phase B: Docker Compose の追加

目的は、`dockerCompose` を 2 つ目の管理対象スタックとして同梱することである。

| 内容 | 完了条件 |
| --- | --- |
| プロジェクト名の決定（`projectName`、`name:`、ディレクトリ名）と検証 | `docs/SPEC.md` 6.7 と `docs/SCHEMA.md` 7.2 の規則をテストで確認 |
| `DockerComposeStackDriver`（`ps` の解析、`up -d`、`stop`） | 状態分類と禁止操作のテスト、実 Docker Desktop での手動確認（利用者の承認のもとで実施） |
| 編集画面の Compose 入力欄、確認シートの Compose 行 | 引き継ぎ・復旧・起動失敗の各確認を画面で確認 |

## 2. その後の優先項目

### 2.1 既存定義からの取り込み

目的は、既存の定義からプロセスとスタックの候補を作り、手入力を減らすことである。

2026-11-12 に初回スコープを `package.json` の scripts と Compose に決定した。追加・編集画面で作業ディレクトリ直下の候補を読み込み、初期選択0件から利用者が選び、フォームで確認して保存する。manager は lockfile 1種類なら根拠とともに提示し、未検出・競合時は利用者が選択する。仕様と受け入れ条件は `docs/SPEC.md` 15.6・18章に記載する。

初回スコープは実装済み。ビルド、新規15テスト、候補画面の描画を確認した。全594テストでは実プロセス同定・引き継ぎの28件が失敗し、変更前の `76fde79` でも同じ28件が失敗することを確認した。この実行環境では `kern.bootsessionuuid` の読み取りが拒否される。テストは弱めたりスキップしたりしていない。実機での候補選択から保存までの通し操作は未確認。

Procfile は後続とする。環境変数・パイプ・リダイレクト等を含むコマンドを、構造化した実行ファイル・引数へどう取り込むかを先に決める。workspace の再帰探索と、Compose のサービス・profile・ポートの解析も初回には含めない。

### 2.2 readiness 判定

2026-11-12 に PM 判断で保留とした。確認用 URL の入力負担に見合う具体的な困りごとがまだ確認できていないため、表示専用の実装も今回には含めない。着手したコード差分は撤回し、起動成功は引き続き既定3秒の生存確認で判定する。「起動済みだが応答できない」ことが実際の支障になった時点で再検討する。

目的は、「起動済み（プロセスが生存している）」から一歩進めて、「応答できる」ことを表示・待機できるようにすることである。

壁は、設定ポートへ HTTP リクエストを送ると、同じポートを先に取った別プロセスの応答を自分の応答と誤認することである（現行仕様で HTTP 判定を撤回した理由）。対象プロセスのプロセスグループが実際に listen しているポートに限って問い合わせる、Compose の healthcheck を使う、などの判定根拠を設計し直す必要がある。

### 2.3 英語 UI と英語の文書

2026-11-12 に次の検討対象とし、日本語を維持した日本語・英語の両対応を PM が選択した。UI は Mac の言語設定に従って切り替える。英語への全面置換は行わない。

目的は、社外の開発者が使えるようにすることである。

Core の型付きエラー・状態を維持し、表示文言はキーと引数を分離して UI 側の String Catalog で翻訳する。起動時に言語を選択し、既存の文字列の理由も選択言語で組み立てる。画面、確認、エラー、コピー用ガイド、`docs/en/` を対応範囲とする。設定の保存形式と外部ログ本文は変更しない。実行途中の言語切替と、既存の全エラー理由を新しい型へ置き換える変更は含めない。

2026-11-12 に上記を実装した。803 件の日英翻訳、同梱リソース、英語文書、コピー用ガイド、CI の翻訳整合性チェックを追加した。停止済みと停止処理中の英訳を区別するため、操作進捗の日本語も「停止処理中」に揃えた。

検証: `python3 scripts/localization.py --check`、`plutil -lint packaging/Info.plist`、`swift build --disable-sandbox --scratch-path /private/tmp/dev-switcher-bilingual-20261112` は成功。SwiftPM 内側の sandbox がこの実行環境で失敗するため同オプションを用いた。`swift test` も同オプションで全 603 件を実行し、574 件成功・29 件失敗。失敗は変更前と同じ実プロセス同定・引き継ぎ関連のテストで、追加した日英 9 件は全件成功した。全翻訳・引数・言語選択・状態表示・両言語ガイド・保存 JSON の不変・移動したアプリの同梱物・翻訳欠落時のエラー・最小サイズのレイアウトを検証した。

英語の詳細説明と確認シートは補助画像で確認した。画像生成では AppKit の入力欄・ログ欄や ScrollView 全体を描画できないため、編集画面を含む実画面全体の目視確認、Mac のアプリ個別言語設定からの切替と再起動は未検証。実 Docker・Supabase の起動停止、署名・配布は今回実施していない。

同日の見直しで、40 箇所の断片連結を文全体の翻訳へ統合し、停止コマンド名と起動対象件数も引数付きの文言へ整理した。未使用キーを削除した結果、翻訳は 757 件。画面とガイドの起動時言語を共有し、引数置換の正規表現を再利用する。生成処理は翻訳・ガイドの全入力を検証してから書き込む。英語欠落・引数不一致・ガイド節欠落で生成済みファイルが変わらないことと、`--check` が古い生成物を変更せず検出することを確認した。再ビルドと日英 9 件は成功、全 603 件は 574 件成功・変更前と同じ 29 件失敗。補助画像の出力コードは削除し、レイアウトの検証は残した。検証結果を本節に残し、このセッションの一時ビルド・画像・抽出スクリプト・ログを削除した。

### 2.4 署名・公証・Homebrew cask

目的は、チーム外へ配布し、更新を容易にすることである。2026-11-12 に MIT の LICENSE、README、公開リポジトリでも動く Release workflow を整備した。Developer ID 署名と公証を付けた DMG を下書きとして作り、実機確認後に公開する（`DISTRIBUTION.md`）。固定名の `DevSwitcher.dmg` とバージョン付き DMG を用意し、DMG とアプリに LICENSE を同梱する。

リポジトリの Public 化と新しい配布物の公開は未実施。Homebrew cask には公開されたダウンロード URL と安定したバージョン付けが必要であり、まだ追加していない。同日、Sparkle 2.10.1 による自動確認・通知と利用者操作による更新を追加した。更新メニュー、配布物への Framework 同梱・署名、EdDSA 署名付き appcast の生成、鍵の初回設定スクリプトを整備した。GitEdit と同じ既存鍵を使い、GitHub の Secret / Variable への登録まで完了した。新規の鍵生成・ローテーションはしていない。

検証: Swift の追加 5 件、配布設定の Python 10 件、翻訳・plist・YAML・shell 構文は成功。全 Swift テストは 608 件中 579 件成功・変更前と同じ 29 件失敗（実プロセス同定・引き継ぎ）。Apple Silicon / Intel 向けの Release ビルド、Universal アプリと Sparkle の同梱、内側からの ad-hoc 署名・厳密検証、両ライセンスの同梱を確認した。独立した検証アプリで、開発ビルドの案内、更新メニュー、Sparkle の取得エラー、自動確認オフの再起動後の保持を確認した。既存鍵で ZIP を署名し、公式 `sign_update` で正当な署名の受理と改ざん後の拒否を確認した。

未検証: 実 DMG の生成は `hdiutil: create failed - 装置が構成されていません` で失敗。公式 `generate_appcast` も、この実行環境では展開した `.app` を対応する bundle と判定できず失敗した。appcast スクリプトは署名ツールを差し替えた検証まで。Developer ID 署名・公証、公開リリース、実際の旧版から新版への入れ替えは未実施。公開済みの v0.1.1 には Sparkle がないため、v1.0.0 の公開前に更新の通し操作を試すには別の旧ビルドと検証用フィードが必要。ローカルの Xcode 27 では SwiftPM の sandbox 無効化と一時ディレクトリのビルド先を使用した。配布開始前に `DISTRIBUTION.md` の実機確認を行う。

### 2.5 メニューバーとグローバルホットキー

目的は、切替の操作を速くすることである（現状はウィンドウで 3 操作）。

壁は、メニューバーのアイコンがノッチの裏に隠れる環境でホットキーが必須になること、外部依存なしのグローバルホットキーは Carbon の `RegisterEventHotKey` などに頼ること、操作面が 2 つになるため切替中の表示と排他の設計が必要なことである。メニューバーに載せるのは状態表示と切替だけとし、ログや編集はウィンドウに残す。
